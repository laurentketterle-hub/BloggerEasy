Building Resilient CLI Tools in Rust

Lessons from rewriting our deployment pipeline in 300 lines

2026-07-28 8 min read laurentketterle
rustclidevopssystems

Six months ago our deployment pipeline was a 2,400-line Bash monster that nobody wanted to touch. Today it compiles to a 4 MiB static binary and deploys in under three seconds. Here is the full story — the design choices, the mistakes, and the patterns that stuck.

The starting point: why Bash broke

Our pipeline handled 14 services across 3 environments. The Bash script had accumulated:

  • Implicit state via exported variables
  • No error handling — set -e was bolted on after the fact
  • Stringly-typed config that relied on grep | awk | sed chains
  • Zero testability — every change was a production coin-flip
⚠️ The key insight: Bash is an excellent glue language for 20-line scripts but becomes exponentially dangerous past 200 lines. Static types and algebraic error handling are not luxuries — they are survival tools.

Why Rust over Go or Python

We considered three options seriously:

  • Python — too slow to start, dependency hell on air-gapped prod hosts
  • Go — strong contender, but error-handling verbosity was a dealbreaker
  • Rust — single binary, clap for args, anyhow/thiserror for errors, serde for config

The clincher: clap's derive macro meant our entire CLI surface was defined in a single struct. No manual arg parsing, no stringly-typed flags.

// The entire CLI definition in one struct
use clap::{Parser, Subcommand};

#[derive(Parser)]
#[command(name = "deployctl", version)]
struct Cli {
    #[arg(short, long, env = "DEPLOY_ENV")]
    env: Environment,

    #[command(subcommand)]
    command: Command,
}

#[derive(Subcommand)]
enum Command {
    Deploy { service: String, tag: String },
    Rollback { service: String },
    Status { #[arg(long)] watch: bool },
}

Error handling: the anyhow + thiserror pattern

We used thiserror for library-level error types and anyhow at the application boundary. This gave us structured errors internally with human-readable context at the top level.

#[derive(Error, Debug)]
pub enum DeployError {
    #[error("cannot reach {host}:{port}")]
    SshConnection { host: String, port: u16 },

    #[error("health check failed after {attempts} attempts")]
    HealthCheck { service: String, attempts: u32 },

    #[error(transparent)]
    Io(#[from] std::io::Error),
}
✅ Result: Every deployment failure now produces a structured error that our monitoring stack can alert on — no more grepping through Bash output.

Config: TOML with serde

Gone are the days of source .env.production and hoping the right variables are set. Our config is now a single TOML file validated at startup:

deployctl deploy --service api-gateway --tag v2.4.1
▸ Reading deploy.toml... OK ▸ Validating 14 service definitions... OK ▸ Connecting to bastion (prod)... OK ▸ api-gateway v2.4.1 → 3 hosts (canary → stable)... DONE in 2.8s

Testing: unit + integration + golden files

We structured tests in three layers:

  1. Unit tests — pure functions, fast, parallel
  2. Integration tests — SSH against Docker containers, real but isolated
  3. Golden-file tests — snapshot CLI output, catch regressions instantly

The golden-file approach was particularly effective. Any change to CLI output format triggers a test failure that forces the author to consciously update the snapshot.

What we learned

  1. Static types eliminate entire classes of bugs — environment strings, port numbers, service names all became enums
  2. Single binary distribution is liberating — no Python, no Node, no runtime to manage on prod hosts
  3. Good CLI frameworks change the design — clap made it so easy to add subcommands that we naturally split the monolith into composable pieces
  4. Errors should be values, not strings — structured errors + anyhow context = debuggable production failures
💡 Pro tip: Start with anyhow::Result<T> everywhere. Graduate to thiserror when you need to match on error variants. Don't over-engineer the error types too early.

Next steps

We are exploring tower-style middleware for the deploy pipeline (timeouts, retries, circuit breakers) and a TUI dashboard using ratatui. The static binary approach makes all of this feasible without adding runtime dependencies.
